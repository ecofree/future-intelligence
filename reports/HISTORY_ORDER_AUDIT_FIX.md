日期：2026-11-17。延续 PR #11、分支 `codex/cumulative-pagination-audit`，基于 `a0c478be3f3e15fde541cb224d362d1820f284da`。不新建业务模块，不修改 SQL 迁移、迁移执行器、模型请求、实验、费用、TSA 或 SSRF 配置，不合并 main、不部署生产。

## 缺陷与复现

旧只读脚本把已应用记录先转换成 `version -> sha256`，仅将 applied_at 输出展示，没有参与历史顺序判定。全部文件和哈希匹配时，即使记录顺序是 `0014_b.sql -> 0014_a.sql -> 0015_reconcile.sql`，仍返回 MATCH。已用合成元数据在旧脚本实际复现；这不是对用户 fi_live 的查询或差异来源结论。

## 修复范围

- 纯文件/哈希比较明确标注 historical_order_status=NOT_CHECKED；数据库审计同时检查已记录时间的部分顺序。
- 按带时区时间比较，不把时区表示差异当先后。已记录顺序与完整文件名的规范顺序相反，返回 REVIEW_REQUIRED_ORDER，列出具体前后文件及时间。
- 同一时间戳的多个文件标为 INDETERMINATE_TIED_TIMESTAMPS；SQL 为展示而按文件名排序，不等于实际执行顺序证据。
- 两份不同全名的 0014 仍可接受；仅相同数字前缀不会阻断。0015 文件名也不构成已经完成语义协调的证明。
- 历史未知文件/哈希不符优先保持 BLOCKED_HISTORY_MISMATCH，绝不被顺序检查降级。
- 读取使用 REPEATABLE READ + READ ONLY。退出码2表示需复核或阻断，不写表、不修历史、不应用任何 SQL。

这些是原 fi.migration-audit.v1 的保守漏检修复和附加诊断字段，不改变其已有字段类型。MATCH 仅指本次可观察清单相符、已记录时间没有发现顺序疑点，不证明数据库实际定义等价或允许生产部署；数据库时间也不是独立的执行时间证明。合法的历史倒序加前向协调仍需审阅具体 SQL 和数据库定义，不自动清除疑点。
